### Issues

#### Critical (Must Fix)

**C1. `/api/cv/export-pdf` is an unauthenticated arbitrary-HTML→PDF renderer: confirmed local file read + SSRF into the Docker network.**
`backend/server.py:1611-1632` passes attacker-controlled HTML/CSS to `HTML(string=...).write_pdf()` with WeasyPrint's **default `url_fetcher`**, which resolves `file://` and `http://` URLs. I verified both primitives locally against WeasyPrint (same version family as the container, which runs 70.0):

- `<link rel="attachment" href="file:///tmp/.../secret.txt">` → the file's contents are embedded in the returned PDF. I decompressed the stream and recovered the plaintext. **Confirmed.**
- `<img src="http://127.0.0.1:8909/probe.png">` → the server issued the GET. **Confirmed** in the target's access log.

And the endpoint is live, public and unauthenticated:
```
$ curl -X POST https://apps.lyai.pro/api/cv/export-pdf -d '{"html":"","css":""}'
→ 400          # route exists, no auth in front of it
```
The impact is not theoretical. The backend container bind-mounts `./backend` at `/app`, and:
```
$ docker exec ...backend sh -c "grep -o '^[A-Z_]*=' /app/.env"
MONGO_URL=
DB_NAME=
GEMINI_API_KEY=
```
So `<link rel="attachment" href="file:///app/.env">` hands any internet caller the Gemini API key and the Mongo URL in a downloadable PDF. The container is also attached to `traefik_traefik` and `lyai-desing-decoder_reverse-network`, so the http fetcher reaches every sibling container. `CORS_ORIGINS` defaults to `*` (pre-existing, `server.py:1657`), so this is also drivable from any third-party page in a victim's browser.

Fix: pass an explicit `url_fetcher` that rejects everything except `data:` URIs (this also closes the `rel=attachment` path, since attachments go through the fetcher), e.g.

```python
def _cv_block_fetcher(url, *args, **kwargs):
    if not url.startswith("data:"):
        raise ValueError(f"recurso externo bloqueado en export-pdf: {url[:60]}")
    return weasyprint.default_url_fetcher(url, *args, **kwargs)

HTML(string=body.html, url_fetcher=_cv_block_fetcher).write_pdf(...)
```
No per-task diff could have surfaced this: Task 5's reviewer saw a 20-line handler that matched the plan verbatim, and the plan itself specified the vulnerable call.

#### Important (Should Fix)

**I1. The "zero drift" promise — the spec's entire justification for this architecture — is not achieved, and the test that was supposed to prove it tests a straw man.**
I reproduced the exact payload the export handler builds (`#cvPreview.outerHTML` + every `<style>` block concatenated) and rendered it through WeasyPrint. Three concrete defects in the produced PDF:

- **The page is dark navy.** The exported CSS includes the app chrome, i.e. `body { background: #0b0e14; color: #e4e4e7; }`. Body background propagates to the canvas. The PDF content stream's first fill is literally `0.043137 0.054902 0.078431 rg` over `75 75 643.7 972.5` — the editor's dark UI background painted across the printed page.
- **The CV box runs off the right edge of the paper.** There is no `@page` rule anywhere, so WeasyPrint applies default page margins. `#cvPreview` is `width: 210mm` (= full A4 width) placed inside a 643.7px content area starting at x=75. The white box is emitted as `75 75 793.7 1122.5` — it extends ~75px (2cm) past the page width and is clipped. Result: ~40mm left margin, 0mm right margin, clipped right edge.
- **Typography falls back on 3 of 4 templates.** Only `/XKQQSR+DejaVu-Sans` is embedded. There are no `@font-face` rules or webfont links, and the container has exactly three families: `fc-list` in the backend returns `DejaVu Sans`, `DejaVu Sans Mono`, `DejaVu Serif`. So `Inter` (modern), `Helvetica` (minimal) and `JetBrains Mono` (tech) all silently resolve to DejaVu Sans — precisely the "en pantalla se ve distinto que en el PDF" failure the spec set out to eliminate.

`TestExportPdf.test_export_pdf_returns_selectable_text` passes because it posts `<h1>Ada Lovelace</h1>` — a document that exercises none of this. The invariant is held *structurally* (one template implementation) but not *in outcome*. Fix: send a print-specific stylesheet rather than `document.querySelectorAll('style')` wholesale, add `@page { size: A4; margin: 0 }` (or 15mm with `#cvPreview { width:auto; padding:0 }` for export), and add a regression test that posts the real preview HTML and asserts page geometry / absence of the chrome background.

**I2. Unescaped `innerHTML` — my call: upgrade from Minor, but not for the reason the per-task reviews were weighing.** Having the full picture, the "single-user, client-only" framing holds for *classic* stored XSS (there is deliberately no share-by-URL, and the PDF handed to a recruiter doesn't execute HTML), but it misses two live paths:

- **It's a plain correctness bug with ordinary CV text.** `renderPreview()` interpolates raw state into `innerHTML`, and `renderExpList()`/`renderEduList()` interpolate into `value="${e.company || ''}"`. A company name containing `"` (e.g. `Acme "Labs"`) terminates the attribute on the next re-render — silent data loss. `R&D`, `C++ <-> Python`, `<Head of Eng>` all corrupt the preview and therefore the PDF. This will happen to a real user with no attacker involved.
- **LLM output derived from externally-sourced text reaches `innerHTML`.** `atsResult` renders `data.missing_keywords.join(', ')`, and `summaryOptions` renders `data.options[i]` — both unescaped. `missing_keywords` is Gemini's output over a **job description the user pastes from a third-party job board**. A prompt-injected posting yields keywords containing markup that executes on `apps.lyai.pro` — same origin as every other app on the hub (shared `localStorage`) and as the unauthenticated `/api/*` surface, and within service-worker registration scope now that `5d3b24c` made the hub a PWA. That is attacker-influenced content, not self-XSS.

One `esc()` helper applied at the five interpolation sites fixes both problems. This also hardens C1's input.

**I3. WeasyPrint runs synchronously on the event loop with no payload cap.** `cv_export_pdf` is `async def` and calls the blocking `write_pdf()` directly, and `ExportPdfRequest` has no `max_length` on `html`/`css`. A single large or pathological document (deeply nested CSS, huge tables) stalls *every* endpoint in this container — reduce, upscale, nutri, reverse — not just the CV editor. This is worse than the pre-existing PIL-in-`async def` pattern because the payload is unbounded, attacker-controlled and CPU-heavy. The codebase already knows the idiom (`asyncio.to_thread(_get_rembg_session)` at `server.py:1647`). Wrap the render in `asyncio.to_thread` and add `Field(max_length=...)` to both fields.

**I4. Deployment: a `weasyprint` install failure takes the *whole* backend down, not just this endpoint.** The lazy import isolates the *import*, but `docker-compose.backend.yml` starts the container with `sh -c "pip install -r requirements.txt && uvicorn server:app ..."` — the install runs on **every restart**, and the `&&` means a failed or unreachable-PyPI install means uvicorn never starts. So the shared `requirements.txt` is a single point of failure for all the unrelated endpoints, and adding a dependency with C-library bindings raises that risk. Right now it happens to work (I confirmed `import weasyprint` succeeds in the running container, v70.0), but that's because the current base image happens to carry pango/cairo/harfbuzz — nothing pins or verifies that. Recommend pinning an upper bound (`weasyprint>=62,<71`) and, ideally, baking the system libs plus a real font package into the image rather than relying on runtime `pip install`.
