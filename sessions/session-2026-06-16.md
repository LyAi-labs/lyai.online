## Qué es cada enfoque

- **Lo nuestro hoy (WebView)**: **MapLibre GL JS** (la librería *web*) corre dentro de un `<WebView>` de React Native en Android, y directo en el DOM en Expo Web. El mapa es, en el fondo, una página web embebida que dibuja con WebGL.
- **Nativo (`maplibre-react-native`)**: usa **MapLibre Native** (el SDK móvil en C++ con render Metal/OpenGL nativo) a través de componentes React Native reales. El mapa lo pinta el motor gráfico del propio teléfono.

## Diferencias

| Dimensión | WebView (lo nuestro) | Nativo (`maplibre-react-native`) |
|---|---|---|
| **Render / FPS** | WebGL dentro del WebView (capa extra) → más lento, sobre todo 3D+terreno en gama baja | GPU nativa → más fluido, mejor en terreno 3D |
| **Batería / memoria** | Mayor consumo (motor web + JS) | Menor, optimizado para móvil |
| **Gestos (pinch/rotate/tilt)** | Vía JS/canvas → a veces lag o choca con el scroll de RN | Gestos nativos del SO, suaves |
| **Arranque** | Carga HTML+JS (CDN unpkg) cada vez → latencia + depende de red para la lib | SDK ya compilado en la app, instantáneo |
| **Paso de datos RN↔mapa** | `postMessage` (puente serializado, fricción) | Props/eventos nativos directos |
| **Offline** | Depende de red (CDN de la lib) salvo que se empaquete | Tiles + lib offline nativo |
| **Funciona en Expo Web** | ✅ **Sí** (misma librería) | ❌ **No** → habría que mantener **doble código** (nativo en móvil + maplibre-gl en web) |
| **Peso del APK** | No añade (usa el WebView del sistema) | Añade el SDK al binario |
| **Features punta** | MapLibre GL JS suele ir por delante (globe, line-trim…) | A veces va detrás en novedades |
| **Esfuerzo para nosotros** | Ya está hecho y funciona | **Alto**: reescribir RouteMap3D + AlertMap3D + terreno 3D + capas de ruta con otra API, y gestionar el doble código web/nativo |

## Veredicto para nuestra app

El **factor decisivo es que la app es Expo Web *y* Android**. `maplibre-react-native` **no corre en web**, así que migrar significaría **mantener dos implementaciones del mapa** (una nativa, otra web) — justo lo contrario de la etapa actual ("mejoras incrementales, no exploraciones grandes").

Por eso el agente (y yo) recomendamos **quedarnos en WebView por ahora**: funciona, es código único web+móvil, y la subida a **MapLibre 5 + WebGL2** ya mejora el rendimiento del WebView en Android sin reescribir nada. Dejamos `maplibre-react-native` **anotado como evaluación futura** solo si el rendimiento en móviles de gama baja (Samsung/Xiaomi de prueba) resulta inaceptable tras MapLibre 5.

En resumen: **nativo es más rápido y fluido, pero rompe el código único web/móvil y es esfuerzo alto** — no compensa todavía; el upgrade a MapLibre 5 captura buena parte de la mejora de rendimiento sin ese coste.
