## 1.1 Competidores Estatales (España)

El mercado español de cuidado infantil digital está **fragmentado y dominado por modelos de suscripción** (no por comisión transaccional), lo cual es la grieta estratégica más importante que verás en este informe.

| Plataforma | Modelo de negocio | Estructura de precios (aprox.) | Cobertura | Posicionamiento |
|---|---|---|---|---|
| **Sitly** | Suscripción freemium (líder de tráfico) | Familia paga ~**19–25 €/mes** Premium para contactar; canguro gratis | Nacional / pan-europeo (NL) | Volumen, SEO masivo, autoservicio |
| **Babysits** | Suscripción freemium | ~**15–20 €/mes** Premium | Nacional / global | Clon funcional de Sitly, menor marca en ES |
| **Nannyfy** | Híbrido: marketplace + servicio gestionado | Comisión / paquetes; canguros verificados | Madrid/Barcelona foco urbano | Calidad y verificación, gama media-alta |

**Lecturas clave del modelo competitivo:**

- **El modelo dominante es la suscripción de acceso (pay-to-contact), no la comisión por transacción.** Esto significa que el competidor **cobra por la promesa de contacto, no por el resultado**. El usuario paga 20 € sin garantía de encontrar canguro. Es el mayor punto de fricción y de insatisfacción del sector.
- **Cuota de mercado estimada [estimación fundamentada]:** Sitly + Babysits controlan probablemente **>50–60% del tráfico digital orgánico** en España por dominancia SEO. Nannyfy/Topnanny lideran el **segmento premium gestionado** (mucho menor en volumen, mayor en ticket). Las agencias tradicionales aún capturan una porción enorme del gasto real **offline**.
- **Casi nadie verifica de forma robusta.** La "verificación" suele ser email + perfil autodeclarado. La comprobación de antecedentes penales (delitos sexuales) — legalmente exigible en España para trabajar con menores — **se delega al usuario**, no la garantiza la plataforma.

## 2.2 El problema del Huevo y la Gallina → **Estrategia "Single-Player + Supply-First"**

> **Regla de oro del marketplace:** se arranca por el lado más fácil de captar y más difícil de retener: **la OFERTA (canguros)**. Sin canguros disponibles, la familia abre la app, no ve a nadie y no vuelve nunca. Con canguros pero sin familias, los canguros esperan — coste tolerable a corto plazo.

### FASE 1 (Mes 0–3) — Concentración geográfica extrema: captar OFERTA
**No lances "en Cataluña". Lanza en 2–3 barrios/distritos** (p. ej. Gràcia + Sant Cugat). Densidad > cobertura. Un marketplace líquido en 3 barrios vale más que uno vacío en toda Cataluña.

- **Embajadores universitarios:** reclutadores en campus UB/UAB/UPF/FP de Educación Infantil. Bono por alta verificada.

- **"Single-player value":** da valor al canguro *aunque no haya familias todavía* — perfil profesional verificado descargable/compartible, mini-CV, badge. Así retienes oferta durante el vacío inicial.

### Benchmarks de referencia [estimación fundamentada — marketplaces de servicios locales/care]

| **Tasa de matching exitoso** | — | **≥60–70%** | Ver abajo: clave de rentabilidad |

### ¿Qué % de matching necesitas para ser rentable?

- En el modelo **pay-to-contact** (Sitly), el matching real puede ser bajo (30–40%) y aun así facturan, porque cobran el intento. **Es un modelo que sacrifica satisfacción por ingreso.**
- En un modelo **por comisión/resultado** (recomendado para diferenciarte), **necesitas una tasa de matching exitoso ≥60–70%** para que el LTV cubra el CAC. Por debajo de ~50%, la insatisfacción dispara el churn y la unit economics se rompe.
- **Regla maestra de viabilidad:** **LTV ≥ 3× CAC** y **payback del CAC < 12 meses**. Con ticket medio por reserva de ~25–40 € y comisión del 15–20%, necesitas ~5–8 reservas por familia/año para que el LTV justifique un CAC de 15 €.

> **Recomendación de modelo de negocio:** modelo **híbrido** — comisión por transacción (alineas tu ingreso con el éxito del match, tu gran diferenciador frente a Sitly) **+** suscripción opcional Premium para familias de uso intensivo + **verificación premium** como ingreso del lado oferta. No cobres solo por contactar: ese es exactamente el dolor que vienes a resolver.

## ¿Qué es un harness?

Un **harness** (literalmente "arnés") es la **capa de software que envuelve un LLM** y le da estructura. Sin harness un LLM es solo "endpoint que recibe texto y devuelve texto". Con harness se vuelve un **agente capaz** de actuar en el mundo.

Funciones típicas de un harness:
- **Tool gating**: decide qué tools puede llamar el LLM (Bash, Read, Edit) y bajo qué permisos
- **Context management**: gestiona el historial, compactación cuando crece, persistencia
- **Hooks/middleware**: intercepta antes/después de cada call para validar/loggear/bloquear
- **Output validation**: parsea respuestas, valida schemas, retry si están mal formadas
- **Memory**: persiste aprendizajes entre sesiones
- **Permissions**: define qué archivos/comandos están permitidos
- **Observability**: telemetría, audit, cost tracking
- **Multi-agent orchestration**: si hay >1 agent, coordina entre ellos

**Ejemplos de harnesses conocidos**:
| Harness | Quién lo hace | Para qué |
|---|---|---|
| **Claude Code (CLI)** | Anthropic | Lo que estamos usando · gestiona tools, hooks, memory, permissions |
| **Claude Desktop** | Anthropic | Más simple, sin tools, solo MCP |
| **LangChain · LangGraph** | Comunidad | Construir agents custom |
| **AutoGen · CrewAI** | Microsoft / comunidad | Multi-agent orchestration |
| **Cursor · Aider · Continue** | Productos independientes | Code agents |
| **OpenAI Operator** | OpenAI | Browser agent |

## 🗂 Data structures clave

### Endpoint shape (`RouteEndpoint`)
```ts
{
  kind: 'station' | 'piste' | 'lift' | 'bar_piste',
  label: string,
  stationId?: string,
  lat: number,
  lng: number,
  entityId?: string  // piste_id | lift_slug | entidades.id (bar)
}
```

### Calc3 request
```ts
POST /api/routing/calc3
{
  origen_lat, origen_lng,
  destino_lat, destino_lng,
  skill: 'principiante|intermedio|avanzado|experto',
  objetivo: 'tiempo|facil|escenica|restaurantes',
  incluir_walk_up: boolean,
  hora: int  // 9..16
}
```

### Calc3 response (single route)
```ts
{
  total_min: number,
  steps_count: int,
  skill, objetivo,
  sig_steps: [{ mode, dificultad?, name, station, cum_s, isStop? }],
  all_steps: [{ lat, lng, name, mode_arriving, dificultad, cost_cumulative_s, edge_geom }]
}
```

### Pareto response
```ts
{
  alternatives: {
    tiempo: { total_min, steps, skill, metrics: { lift_segments, ski_segments } },
    facil:  { ... },
    escenica: { ... }
  }
}
```

### Bar-piste ranked (nuevo)
```ts
GET /api/routes/bars-piste-ranked?from_lat&from_lng&to_lat&to_lng[&q&limit]
[{
  id, nombre, estacion_slug, lat, lng,
  dist_to_origin_km, dist_to_dest_km,
  closer_to: 'origin' | 'dest',
  min_dist_km
}]
```
