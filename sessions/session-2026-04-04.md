### 1. ¿Existe un componente "card"?

### 2. ¿Qué datos tiene LyAi?

El schema PostgreSQL ([lyai-core/database/schema.sql](lyai-core/database/schema.sql)) tiene la estructura completa:

| Tabla | Campos clave |
|---|---|
| `entidades` | `tipo` (restaurante/hotel/...), `subtipo`, `lugar_id`, coords |
| `entidad_contenido` | `nombre`, `descripcion` en 5 idiomas |
| `entidad_atributos` | JSONB flexible → aquí irían fotos, precios, ratings |
| `horarios` | por temporada + día semana |
| `disponibilidad` | estado en tiempo real (abierto/cerrado/lleno) |
| `embeddings` | vectores para búsqueda semántica |

**El schema es robusto — está diseñado para esto.** Lo que falta es saber cuántos registros reales hay cargados (necesitaría un `SELECT COUNT(*) FROM entidades` en el servidor para confirmarlo).

### 3. ¿Cómo funciona el flujo del chat?

**Gemini 2.5-flash llamado directamente desde el frontend** — sin N8N, sin backend propio:

```
Usuario escribe → React ChatBar/Conserje → GoogleGenerativeAI(VITE_GEMINI_KEY) → respuesta texto
```

La API key está en `VITE_GEMINI_KEY` (expuesta en el bundle — esto es un problema de seguridad a resolver). El contexto enviado a Gemini son solo los datos hardcodeados de la estación (pistas, nieve, remontes) — **no consulta la DB**.

### Para la card enriquecida — arquitectura recomendada

```
Usuario: "restaurante en Morgins" 
  → Frontend detecta intent (hotel/restaurante/bar)
  → POST al webhook N8N /webhook/lyai-search con {query, station, type}
  → N8N: busca en entidades DB + llama Google Places API
  → N8N: responde {text: "...", card: {name, photo, rating, price, maps_url}}
  → Frontend: renderiza texto + componente BusinessCard
```

El flujo **hybrid** es el correcto: texto inmediato (desde Gemini local) + card en segundo plano (N8N + Google Places). La card se puede añadir como tipo de mensaje nuevo en el array `messages` de Conserje.
