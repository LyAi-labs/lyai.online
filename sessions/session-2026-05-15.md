### Validez jurídica del "IP-proof de GitHub" vs. RPI

| Mecanismo | Valor probatorio | Coste | Recomendación |
|---|---|---|---|
| Commit GitHub (timestamp+SHA) | Prueba **indiciaria** · refutable en juicio (GitHub puede manipular metadata en teoría) | €0 | Mantener — no sustituye nada |
| **RPI España (telemático RePI)** | Prueba **plena** de autoría y fecha · presunción iuris tantum oponible erga omnes · admisible en tribunales UE+CH | €13,59 | ✅ **HACER YA** |
| Sello de tiempo cualificado (eIDAS) | Prueba **plena** equivalente legal a notario · validez transfronteriza UE+CH (eIDAS 2.0) | €5-30 / sello | Alternativa rápida — útil para versiones intermedias |
| Depósito notarial | Prueba plena · más cara · útil para algoritmos secretos | €150-400 | Reservado para el RAG si quieres mantenerlo como secreto industrial |

> **Realidad legal**: GitHub IP-proof **NO es suficiente** ante un litigio en Suiza o ante un troll de marca europeo. Eleva el código a RPI + sello de tiempo eIDAS antes del lanzamiento PdS.

### Lectura cruzada del cuadro

**Tres patrones que LyAi debería interiorizar:**

1. **Las apps B2C puras de esquí con suscripción tienen techo bajo**. Slopes en 10 años llegó a ~$1M ARR. Ski Tracks paga un coste reputacional alto por su $50/año. **FATMAP no sobrevivió standalone** — ni con 1,6M usuarios. Construir un negocio sostenible **solo** con suscripción consumer en una vertical estacional es muy difícil.

2. **Los apps oficiales de destino (Matterhorn, My Epic) no monetizan la app — monetizan el ecosistema**. El forfait, la lección, el F&B, los datos del visitante. La app es **canal**, no producto SKU. Modelo más cercano a LyAi.

3. **El B2B SaaS de conserjería está casi enteramente en hotelería**. Bowo, LoungeUp, Triparound facturan **per-room** (€2–€8/habitación/mes orden de magnitud sectorial) + **comisión sobre ancillary**. Nadie ha cubierto bien el espacio "**conserjería de dominio esquiable institucional**" (estación + comunes + comercios), que es precisamente la vacante de LyAi.

## 2 · Mecanismos de Captura de Valor Local

Cómo estas plataformas cobran a los **comercios físicos del destino turístico** (restaurantes, hoteles, alquileres, guías, transporte).

### A · Comisión por transacción (Viator, TripAdvisor Experiences)
- **Viator cobra ~20% flat** sobre cada experiencia reservada por el huésped.
- Modelo limpio: el operador local (escuela de esquí, guía de raquetas, alquiler) lista gratis y paga solo si hay reserva.
- **Pro:** alineación de incentivos perfecta · cero CAPEX para el comercio.
- **Contra:** comisión de 20% es **dura para márgenes alpinos** (alquileres, escuelas → margen neto 15-25%). Restaurantes de montaña ya rechazan TripAdvisor por esto.

### B · Cost-per-Click puro (Yelp, Google Maps Ads)
- **CPC $2-20 típico**, hasta $40 en sectores con alto valor cliente (servicios profesionales).
- **Yelp Ads:** $300-500/mes SME, $1.000-2.500 mid, $5.000+ premium.
- **Pro:** escalable, comercio paga por demanda observable.
- **Contra:** modelo **incompatible con destinos pequeños** (Champéry tiene 50 comercios — el CPC se desploma sin masa crítica) · agotador para SME locales sin marketing manager.

### C · SaaS plano por propiedad (Bowo, LoungeUp, Triparound modo SaaS)
- **Per-room/mes para hoteles** (€2–€8/habitación es la banda observada en el sector EU, no pública por vendor).
- Per-property/mes para vacation rentals (€30–€150/propiedad/mes según features).
- **Pro:** ingreso recurrente predecible · sin volatilidad estacional ya que se paga 12 meses.
- **Contra:** requiere venta consultiva · ticket inicial alto para SME sin presupuesto digital.

### D · Listado enhanced + featured placement (TripAdvisor Business Advantage)
- **Plan anual fijo** (~€300-700/año típico) para "destacar" la ficha, añadir fotos premium, ocultar competencia visual.
- **Pro:** ARPU estable.
- **Contra:** pierde valor si todos los comercios pagan (race-to-the-bottom).

### E · Hybrid "performance + base" (Booking.com como referencia adyacente)
- **15% comisión sobre reserva** + opción de "preferred partner" (15-25% adicional por ranking boost).
- **Pro:** captura el upside cuando funciona.
- **Contra:** comercio paga doblemente — comisión base + bid por visibilidad.

### F · Modelo "back-end share" institucional (Matterhorn, My Epic)
- La app **no cobra al comercio**. Cobra al **operador del dominio** (Zermatt Bergbahnen, Vail Resorts).
- El operador del dominio recupera la inversión vía aumento del valor del forfait, mejor experiencia que justifica precio premium, datos de visitantes.
- **Pro:** comercios locales reciben **valor gratis** → fácil adopción → marketplace denso → ciclo virtuoso.
- **Contra:** depende de cerrar contrato institucional (la barrera de entrada es **el contrato con la estación**, no la captación capilar de comercios).

### Síntesis aplicable a LyAi · Portes du Soleil

| Modelo | ¿Aplicable a PdS? | Riesgo principal |
|---|---|---|
| Comisión flat 20% (Viator) | Parcial — solo para experiencias guiadas y alquileres premium | Restaurantes alpinos rechazarán por márgenes |
| CPC puro (Yelp) | **No** — masa crítica de comercios insuficiente para subasta | Modelo se desinfla bajo 200 comercios listados |
| SaaS per-room (Bowo) | **Sí** — para los ~80 hoteles del valle | Adopción lenta sin caso de uso probado |
| Featured listing anual | Marginal — útil como upsell, no como base | Cannibaliza neutralidad editorial |
| **Back-end share institucional** | **Recomendado como columna vertebral** | Depende 100% del contrato con Domaines Skiables / comunas |
| **Comisión transparente 8-12% en transacciones (no 20%)** | Recomendado como ingreso variable | Necesita gateway integrado (Stripe Connect) |

## 3 · Propuesta de Modelos Híbridos Habilitados por IA

### Tesis central

Un **Hub Centralizado** que combina (a) **chat conversacional en LN** + (b) **mapas en tiempo real** + (c) **analítica de negocio local** rompe el dilema clásico del sector:

- Las apps B2C suscripción tienen techo bajo y mueren en verano.
- Las plataformas B2B SaaS hotelero son rentables pero verticalmente estrechas.
- Las plataformas tipo TripAdvisor escalan pero erosionan al comercio local.

**El hub IA puede facturar a tres lados a la vez** — institución (back-end share), comercio (transacción con comisión justa) y datos (API a terceros) — porque genera *valor único* en cada uno.

### Arquitectura de ingresos recomendada para LyAi (4 flujos)

#### Flujo 1 — Contrato institucional (B2G/B2B core)
**Cliente:** Domaines Skiables PdS · Office de Tourisme Champéry / Morgins / Les Gets / Avoriaz · Société des Téléphériques.

**Producto:** plataforma white-label "conserjería digital del dominio" incluyendo chat IA, mapa live, ficha de comercios, alertas operativas (météo, avalanche, gestión incidentes).

**Pricing:** **anuidad plurianual €40-90k/año por dominio** (referencia: Bowo cobra ~€50-150k/año a cadenas de 8-15 hoteles · una estación es comparable en complejidad).

**Por qué pagaría la institución:** reduce carga de la oficina de turismo (consultas repetidas), capital político (gestión de alertas en tiempo real), elegibilidad a subvenciones Atout France / Suisse Tourisme / Région AURA / Canton Valais.

**Resiliencia estacional:** contrato anual fijo · cobra los 12 meses · no depende del flujo turístico.

#### Flujo 2 — Comisión transparente sobre transacciones (B2B comercio)
**Cliente:** restaurantes, alquileres de ski, escuelas, guías, transfers, spa, alojamientos no afiliados a OTAs.

**Producto:** gateway de reserva integrado en el chat IA (Stripe Connect) — el huésped reserva una mesa, una clase de ski, un transfer Genève→Champéry directamente en conversación.

**Pricing:** **comisión 8-12%** (la mitad que Viator). Listing gratis. Sin CPC.

**Por qué funciona:** comercio paga solo cuando reserva confirmada · margen aceptable vs 20% Viator · IA conversacional convierte mejor que listado plano (chat de fricción baja).

**Resiliencia estacional:** comercios alpinos tienen 2 temporadas (invierno + verano biking) · si la app sirve ambas, los ingresos se reparten.

#### Flujo 3 — Tier Premium B2C opcional (no como columna)
**Cliente:** usuario final (turista PdS, abonado de temporada).

**Producto:** suscripción "**LyAi+**" desbloqueando analítica avanzada (estilo Slopes), mapas offline (estilo FATMAP), prioridad de soporte conserje humano.

**Pricing:** **€19-29/temporada** (no anual auto-renovable — el modelo "season pass" no auto-renovable es lo que aceptan los usuarios EU según Slopes y Ski Tracks; las auto-renovaciones provocan backlash).

**Por qué aquí va el "Premium" y no como core:** es ingreso accesorio · si llega es bienvenido, si no llega el negocio no muere. Slopes prueba que con $24,99/año un indie llega a $1M ARR pero **ese techo no soporta una empresa con sueldos suizos**.

**Resiliencia estacional:** combinada con módulo verano (rutas senderismo, biking, lacs alpins) la suscripción se vende **2 veces** — pase invierno + pase verano.

#### Flujo 4 — API de datos + Inteligencia de Negocio (B2B2B)
**Cliente:** OTAs (Booking, Airbnb · datos meteo y aforo), aseguradoras (riesgo de avalancha y siniestralidad), agencias turísticas regionales (analítica de flujos), inmobiliarias alpinas (analítica de demanda local).

**Producto:** API B2B con feed agregado y anonimizado de: ocupación de remontes en tiempo real, demanda de comercios (qué buscan los huéspedes), patrones de consulta del chat, alertas meteorológicas curadas.

**Pricing:** referencia Mountain News (OnTheSnow Partner API) cobra licenses **$10-50k/año** por feed a media companies y financial institutions · Zyla API Hub estructura por tramos de calls.

**Por qué es importante:** este flujo **no requiere más ningún esfuerzo operativo** — los datos ya existen porque los genera la propia operación de los flujos 1-3. Es **margen prácticamente 100%**.

**Resiliencia estacional:** APIs B2B se contratan por años, indiferente al flujo turístico.

### Síntesis de ingresos proyectados (orden de magnitud · año 3 post-lanzamiento)

| Flujo | Clientes año 3 | Revenue año 3 (orden) | % del mix | Resiliencia |
|---|---|---|---|---|
| 1 · Contratos institucionales | 3-5 dominios alpinos | €180-400k | 55-65% | Alta (anual) |
| 2 · Comisiones transaccionales | 200-400 comercios | €60-150k | 18-22% | Media (estacional) |
| 3 · Tier Premium B2C | 2.000-5.000 abonados | €40-130k | 10-15% | Baja (temporal) |
| 4 · API B2B datos | 2-4 contratos | €30-120k | 8-15% | Alta (anual) |
| **Total año 3** | | **€310-800k ARR** | 100% | Diversificada |

**Por qué este mix es resiliente:**

1. **65% del revenue (flujos 1 + 4) no depende del flujo turístico** — son contratos anuales B2B/B2G.
2. **Los flujos transaccionales (2 + 3) se duplican con módulo verano** (MTB, hiking, lacs) usando misma infraestructura — patrón ya validado por Steamboat (35% revenue verano) y considerado por Slopes.
3. **La IA conversacional es el conector entre los 4 flujos**: el chat sirve al turista (flujo 3), genera leads para el comercio (flujo 2), produce datos para el feed (flujo 4) y demuestra valor a la institución (flujo 1).

### Diferencial competitivo defendible

Ningún player actual combina los 4 flujos:

| Player | Flujo 1 inst. | Flujo 2 comisión | Flujo 3 B2C | Flujo 4 API datos |
|---|---|---|---|---|
| Slopes | ❌ | ❌ | ✅ | ❌ |
| FATMAP/Strava | ❌ | ❌ | ✅ | parcial |
| Matterhorn App | ✅ | ❌ | parcial | ❌ |
| Triparound | ❌ | ✅ | ❌ | ❌ |
| TripAdvisor/Viator | ❌ | ✅ | ❌ | parcial |
| **LyAi (propuesta)** | ✅ | ✅ | ✅ | ✅ |

**El moat estratégico:** ser **el contrato firmado** con Portes du Soleil. Una vez dentro, los flujos 2/3/4 se acumulan sobre la misma infraestructura y nadie puede replicarlo sin el contrato institucional — exactamente lo opuesto al modelo "ataca-el-comercio-uno-a-uno" de Viator/Yelp.

## Conclusión analítica

El sector demuestra dos verdades operativas:

1. **Los modelos puros (solo B2C suscripción, solo SaaS hotelero, solo comisión OTA) tienen techo o vulnerabilidad estacional**. Hasta gigantes como FATMAP han debido fusionarse o desaparecer.

2. **El valor recurrente y resiliente se captura en el centro del ecosistema turístico de destino** — donde institución, comercio y huésped convergen. Ese centro hoy está vacío en los dominios alpinos europeos.

LyAi tiene la oportunidad **estructural** de ocuparlo en Portes du Soleil con un mix de 4 flujos que se refuerzan entre sí, donde el contrato institucional es el ancla y la IA conversacional es el conector. La métrica clave para validar viabilidad año 1 es **un primer contrato institucional firmado** (Champéry, Morgins, o el grupo Domaines Skiables). Sin él, los flujos 2-4 son aspiracionales; con él, son ejecución.

### Pipeline de migración sin pérdida (5 pasos)

```
Paso 1 · Snapshot baseline (defensa)
  ├── mongodump --uri="..." --out=/opt/lyai/backups/mongo-pre-migration-YYYY-MM-DD/
  └── pg_dump full · lyai_db
  
Paso 2 · Schema analysis · script Python
  ├── Por cada colección: list fields + cardinalities + sample
  └── Output: migration_plan.md por colección
  
Paso 3 · DDL Postgres (crear tablas/columnas faltantes)
  ├── lyai.alertas (CREATE TABLE)
  ├── lyai.business_updates (CREATE TABLE)
  ├── ALTER lyai.lugares ADD COLUMN weather_temp_c, snow_depth_cm...
  └── Test inserts dummy + rollback
  
Paso 4 · Migration script (idempotente)
  ├── Mongo → PG row by row
  ├── ON CONFLICT DO UPDATE (idempotente · puede re-correr)
  ├── Logs cada 100 docs + checksums
  └── Dry-run mode primero (count only)
  
Paso 5 · Validación dual (1-2 semanas)
  ├── Chat + endpoints leen de AMBAS DBs · comparan resultados
  ├── Log discrepancies a tabla `migration_diff`
  ├── Si diff < 0.1% durante 7 días consecutivos → cutover
  ├── Cutover: feature flag flip · solo PG
  └── 7 días más de validación · si OK → DROP Mongo collections
```

### Riesgos & mitigaciones

| Riesgo | Probabilidad | Mitigación |
|---|---|---|
| Pérdida de docs en migración | Baja | Idempotent script + counts + checksums |
| Schema diff sutil (campo opcional faltante) | Media | Schema analysis exhaustivo previo + JSON dump per collection |
| Encoding (caracteres FR especiales) | Baja | Mongo y PG usan UTF-8 · validar `ç`, `é`, `ñ` con grep |
| Timestamps timezone diff (Mongo BSON UTC vs PG timestamptz) | Media | Conversión explícita en script · validar 5 docs random |
| Application reads stale Mongo durante migración | Alta | **Dual-read** durante validación · luego cutover atómico |
| Backup/restore size (índices grandes) | Baja | pg_dump custom format + compression |
| Mongo dependiente en otros servicios desconocidos | Media | Inspeccionar TODOS los consumidores de Mongo antes de DROP |
