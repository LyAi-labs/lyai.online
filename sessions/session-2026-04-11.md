## 3. Elevation Profile

Add `"elevation": true` to the POST body. Coordinates in the response become `[lon, lat, altitude_m]` (3D). For extra slope data, add `"extra_info": ["steepness"]` — returns interval segments with steepness grades (-5 to +5).

---

## 4. API Endpoint + Example Call (Champéry → Morgins)

**Endpoint:** `POST https://api.openrouteservice.org/v2/directions/{profile}/geojson`

```bash
curl -X POST \
  "https://api.openrouteservice.org/v2/directions/foot-hiking/geojson" \
  -H "Authorization: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "coordinates": [
      [6.8697, 46.1739],
      [6.8519, 46.2382]
    ],
    "elevation": true,
    "extra_info": ["steepness", "surface", "traildifficulty"],
    "instructions": false
  }'
```

Note: coordinates are `[longitude, latitude]` order (GeoJSON standard).

---

## 5. Leaflet Compatibility

**Yes, direct drop-in.** Use the `/geojson` endpoint variant — it returns a proper GeoJSON `FeatureCollection`. Pass it straight to `L.geoJSON()`:

```javascript
const response = await fetch(
  "https://api.openrouteservice.org/v2/directions/foot-hiking/geojson",
  {
    method: "POST",
    headers: {
      "Authorization": "YOUR_API_KEY",
      "Content-Type": "application/json"
    },
    body: JSON.stringify({
      coordinates: [[6.8697, 46.1739], [6.8519, 46.2382]],
      elevation: true,
      extra_info: ["steepness"]
    })
  }
);
const geojson = await response.json();
L.geoJSON(geojson).addTo(map); // works directly
```

If you use the non-`/geojson` endpoint, it returns an encoded polyline — you'd need to decode it manually.

**Cambio crítico #1: Scratchpad.md sobre agents_db para estado de agentes**

Cursor probó que el estado no necesita una BD centralizada. Cada agente mantiene un `scratchpad.md` en su workspace que se **reescribe** (nunca append) al alcanzar el umbral de contexto. Más simple, auditable, cero infraestructura extra.

**Cambio crítico #2: Handoff messages como protocolo de entrega**

En lugar de solo escribir resultado en DB, cada worker entrega un handoff estructurado al Nexus al completar:
```
- Tarea completada / fallida
- Hallazgos no esperados
- Concerns o bloqueos detectados
- Archivos modificados
- Qué NO se hizo y por qué
```
Este handoff sube al Planner (Nexus), que adapta la cola dinámicamente.

**Cambio crítico #3: Ciclo de auto-summarización en cada worker**

Los workers tienen sesiones largas. Sin summarización, el drift es inevitable. El ciclo:
```
1. Worker ejecuta hasta N tokens de contexto
2. Se inserta synthetic query: "Resume el estado actual de tu tarea"
3. Worker genera resumen ~500-1000 tokens
4. Continúa con contexto comprimido + resumen
```
Implementable con el Anthropic SDK (no requiere fine-tuning): se fuerza via prompt al alcanzar el umbral.
